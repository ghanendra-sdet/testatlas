# Community Roadmap

`ROADMAP.md` tracks version milestones for maintainers. This document is the same information from the other direction — what's coming, and specifically how you can influence it. If you only read one roadmap document, and you're not building TestAtlas's internals, read this one.

## Where things stand

Eleven learning paths are live — Foundations plus ten certified Reference Curricula (Manual Testing, API Testing, Test Automation, Database Testing, Performance Testing, AI for QA, Mobile Testing, Security Testing, Interview Preparation, Career & Leadership) — 225 modules total, all reviewed against the same standard. `v1.0.0` shipped with the first three plus Foundations; every path since has extended that same released, stable platform. See `PROJECT_VISION.md` and `ROADMAP.md` for what that means day to day and how the releases sequenced.

## What's next, and why it's not decided yet

The honest answer: **we're waiting to hear from you before deciding what comes after these eleven paths.** Two broad directions are on the table, and real feedback should decide the balance between them, not a guess made in isolation:

**More depth on what already exists** — hands-on practice to go with the reading: a sample application to actually test, sample REST APIs, practice bug reports, mock code review, interview-style challenges. This turns TestAtlas from something you read into something you *do*. `ROADMAP.md` names this direction Project Simulations + Labs.

**More breadth** — a twelfth full learning path. No specific candidate is committed; whatever it is gets a written architecture proposal reviewed and approved before content is written, the same way every path so far has been built.

## How to actually influence this

- **Open a Learning Path Proposal issue** if you have a specific case for what should come next — see `AUTHOR_GUIDE.md` for the format. A concrete "here's the learner problem, here's why it matters" pitch carries more weight than a vote.
- **Use the 💡 Ideas discussion category** (see `docs/community/DISCUSSION_CATEGORIES.md`) for something earlier-stage than a formal proposal.
- **Tell us what you used TestAtlas for** — studying for a role, preparing for an interview, onboarding a team. Real usage patterns are the actual signal that should drive prioritization, more than any single feature request.
- **File Content Correction and Bug Report issues** as you find them — a resource that's accurate and reliable matters more than one that's merely bigger.

## What we're deliberately not doing yet

- **Not starting a twelfth full learning path immediately.** Per `PROJECT_CONSTITUTION.md`'s own stated value — "a smaller collection of trusted, well-connected resources is better than a large collection of inconsistent pages" — adding breadth before gathering real feedback risks building the wrong thing carefully instead of the right thing at all.
- **Not committing to a fixed next-release scope or date.** See `docs/architecture/VERSIONING_STRATEGY.md`'s own history — TestAtlas's actual pace has repeatedly outrun speculative planning; committing to specifics before real evidence exists has already proven unreliable once.

## Every future path follows the same standard

Whatever comes next — a new learning path, hands-on labs, anything structural — gets built against `docs/architecture/REFERENCE_CURRICULUM_CERTIFICATION.md`'s certified defaults, proposed and reviewed before content is written, the same way every path so far was built. Growth doesn't mean lowering the bar; it means applying the same bar more times.
